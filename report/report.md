## 一、实验目的

本实验要解决的是：内核被中断或异常打断之后，怎样接管控制权、完成处理，再回到正确的位置执行。

我们重点关注四件事：

1. 区分硬件自动记录的状态和软件仍需保存的寄存器现场。
2. 使汇编入口、`struct trapframe` 与 C 函数的调用约定保持一致。
3. 正确处理断点、非法指令和持续发生的时钟中断。
4. 将 Lab2 的内存管理接入 Lab3，并保留新框架中的中断保护。

完成这些内容后，内核具备了基本的 Trap 处理能力。但它还没有用户进程和调度器，本次保存现场再返回，也不等于已经实现进程切换。

## 三、从启动到返回：先把执行流串起来

### 3.1 中断入口建立之前，先处理哪些依赖

Lab3 的基础包并没有直接包含我们在 Lab2 中补写的全部功能。`pmm.c` 和 `best_fit_pmm.c` 都留下了迁移位置。因此，开始实现 Trap 时，还需要先恢复可以工作的物理页管理。

这里容易混淆“设置入口”和“允许中断发生”。当前 `kern_init()` 在 `pmm_init()` 前后各调用了一次 `idt_init()`，它们都把 `stvec` 指向 `__alltraps`，并没有打开全局中断。物理内存初始化完成后，`clock_init()` 才设置第一次定时事件和时钟中断源使能，最后由 `intr_enable()` 打开 S 态全局中断开关。

按当前源码，主要顺序是：

```text
清零 BSS → dtb_init() → 控制台初始化 → 输出内核信息
        → idt_init() → pmm_init() → idt_init()
        → clock_init() → intr_enable() → 内核等待循环
```

因此，不能简单地把它概括成“内存初始化之前没有设置中断入口”。真正需要保证的是：在打开中断之前，入口、处理函数和恢复路径都已经可用。

### 3.2 一次 Trap 的完整路径

```text
中断到来，或者当前指令触发异常
  ↓
硬件记录返回位置、原因及相关状态，转入 stvec 指定的入口
  ↓
__alltraps：SAVE_ALL 将通用寄存器和 CSR 字段保存到栈上
  ↓
mv a0, sp；jal trap：把 Trap frame 交给 C 函数
  ↓
trap_dispatch()
  ├─ 中断 → interrupt_handler()
  └─ 异常 → exception_handler()
  ↓
__trapret：RESTORE_ALL 读取处理后的 Trap frame
  ↓
sret：按恢复后的状态和 sepc 返回
```

我们据此划分两个模块的边界：模块一负责让现场完整地进入和离开处理流程；模块二决定遇到具体事件时应做什么。两者之间传递的是同一个 `trapframe`，处理函数对它的合法修改必须在返回时生效。

### 4.1 前置任务：迁移 Lab2 的内存管理

#### 4.1.1 `page_init()`：迁移前先检查依赖

负责人：王雅枫（2412832）。涉及 `kern/mm/pmm.c` 和 `kern/mm/memlayout.h`。

迁移时先对比了两个实验的 `Page` 结构、设备树接口、地址转换宏和初始化调用关系。`get_memory_base()`、`get_memory_size()`、`pa2page()` 和描述符字段仍能沿用，但旧函数使用的两个地址宏没有出现在新框架中，于是依据 Lab3 已有布局补齐：

```c
#define KERNEL_BEGIN_PADDR  (KERNBASE - PHYSICAL_MEMORY_OFFSET)
#define PHYSICAL_MEMORY_END (KERNTOP - PHYSICAL_MEMORY_OFFSET)
```

这两个值由当前映射关系推导，避免再维护一组独立的固定地址。另一个需要保留的变化是：Lab3 在分配、释放和查询空闲页的接口外增加了中断状态保存与恢复。迁移采用补入 `page_init()` 的方式，保留新框架的这些接口。

`page_init()` 的工作可以分为三段：

1. 校验设备树信息，并将管理上界限制在框架可覆盖的范围内，再向下按页对齐。
2. 从当前内核 `end` 之后安排描述符数组，检查所需空间和地址运算，再计算向上按页对齐的空闲起点。
3. 将描述符置为已保留的初始状态，只把元数据之后的完整页面交给 `init_memmap()`。

我们核对时特别区分了四种量：`pages` 是描述符数组的虚拟地址，数组下标是描述符索引，`nbase` 是 DRAM 起始物理页号，`npage` 是物理页号的排他上界。因此，描述符数量应为 `npage - nbase`，不能直接把 `npage` 当作实际页数。

迁移后也继续保留溢出、内核覆盖范围、描述符容量和空闲页数量的检查。必须先确认元数据放得下，再开始写描述符；如果此时越界，后面的分配器自检已经无法补救。

#### 4.1.2 Best-Fit：保持分配器接口一致

负责人：胡楚骅（2413276）。涉及 `kern/mm/best_fit_pmm.c` 及管理器选择。

迁入的 Best-Fit 使用按地址排列的空闲链表。分配时寻找能够满足请求的最小块，剩余部分重新进入空闲链表；释放时按地址插入，并尝试与前后相邻块合并。最后在 `init_pmm_manager()` 中选择 `best_fit_pmm_manager`。

`page_init()` 只通过统一的 `init_memmap()` 接口注册空闲页面，不需要知道后面采用哪一种分配算法。这也是我们能够分开迁移、最后接入同一个管理器接口的原因。

### 4.2 模块一：Trap 入口与上下文恢复

负责人：胡楚骅（2413276）。涉及 `kern/trap/trapentry.S`。

#### 4.2.1 先确定保存格式，再写恢复代码

本模块最先要确定的是：处理函数拿到的指针到底指向什么。RV64 下 `SAVE_ALL` 在当前栈上分配 36 个槽位，每个槽位 8 字节，共 288 字节，与 `struct trapframe` 对应。

| 槽位 | 保存内容 | 恢复时的作用 |
|---|---|---|
| 0～31 | 通用寄存器的对应字段；槽位 2 为原来的 `sp` | 恢复原执行流的整数寄存器现场 |
| 32 | `sstatus` | 为 Trap 返回提供状态 |
| 33 | `sepc` | 决定返回后的指令位置 |
| 34 | `sbadaddr`，即旧命名的 `stval` | 保存诊断信息 |
| 35 | `scause` | 判断事件原因 |

`sp` 的保存方式与其他寄存器不同。入口先用 `sscratch` 暂存旧 `sp`，再减小 `sp` 分配现场空间，随后才把旧值取出放入槽位 2。如果恢复时只简单地把栈指针加回一个常数，就没有真正采用 Trap frame 中保存的 `sp`。

当前实现也没有根据 `sscratch` 切换用户栈和内核栈。它服务于本实验已有的内核态执行流，不能仅凭这一个 CSR 就认定已经支持完整的用户态陷入。

#### 4.2.2 第一步：建立汇编到 C 的调用

`SAVE_ALL` 之后增加：

```asm
mv a0, sp
jal trap
```

此时 `sp` 正好指向 Trap frame。按 RISC-V 调用约定，`a0` 是第一个参数，`jal` 则建立 C 函数返回到汇编的地址。原执行流的 `a0` 和 `ra` 已经保存，所以这两条指令可以使用它们，而不会丢失被打断的现场。

这一部分的规格没有规定复杂的指令序列，而是约束调用前后的状态：传入的 `tf` 必须等于调用前的 `sp`；C 函数正常返回后，`sp` 仍指向同一个现场，执行流顺接 `__trapret`。

#### 4.2.3 第二步：恢复顺序由寄存器用途决定

`RESTORE_ALL` 先把槽位 32、33 读入 `s0`、`s1`，再分别写回 `sstatus` 和 `sepc`。接着恢复通用寄存器，包括刚才作为中转使用的 `s0`、`s1`，最后恢复槽位 2 中的旧 `sp`。

这里有两个顺序约束：

- `s0`、`s1` 先用作 CSR 的中转，等中转完成后再恢复它们自己的最终值。
- 其余字段都依赖当前 `sp` 定位，因此旧 `sp` 必须最后读取。最后那条 `LOAD x2, 2*REGBYTES(sp)` 仍然用修改前的栈指针计算读取地址。

我们还把“恢复处理后的现场”写进了规格。如果模块二调整了 `tf->epc`，恢复宏就应把新值写回 `sepc`；恢复宏自己再加一次偏移，反而会破坏两个模块的约定。

`sret` 根据 `SPP` 选择返回特权级，并将 `SPIE` 恢复给 `SIE`，返回位置来自 `sepc`。这些状态变化由指令完成，恢复宏不需要额外打开中断。[RISC-V S 态状态寄存器说明](https://docs.riscv.org/reference/isa/v20260120/priv/supervisor.html#_supervisor_status_sstatus_register)

#### 4.2.4 提示词与实际迭代

模块一分两轮实现。第一轮只补入口调用，第二轮再补恢复宏。两轮提示词都保留 `SAVE_ALL`、结构体和 `trap()` 接口，并约束 `sp` 的使用。完整原文保留在附录 A，实际回复和当时验证记录见 [prompt.md](prompt.md)。

第一轮的目标是确认参数传递和返回衔接；第二轮再对照槽位逐项补齐恢复。这样每一轮可以解释自己新加了什么，也能看出当前错误是否由尚未实现的另一部分引起。

早期 `make` 和 `make qemu` 因 `interrupt_handler()`、`exception_handler()` 尚未声明和实现而失败，单独构建汇编入口又遇到 `sbadaddr` 名称兼容问题。当时的记录明确保留“未完成运行验证”。这两个现象没有被当作上下文恢复逻辑已经错误的证据：前者需要等待模块二接入，后者需要核对工具链。最终整合后的断点返回和寄存器检查通过，才补上运行层面的验证。

### 4.3 模块二：中断与异常处理

负责人：罗元伟（2412737）。涉及 `kern/trap/trap.c`。

```c
void interrupt_handler(struct trapframe *tf);
void exception_handler(struct trapframe *tf);
static size_t trap_insn_len(uintptr_t epc);
```

#### 4.3.1 先分类，再讨论每类事件的处理

已有 `trap_dispatch()` 将 `cause` 转成有符号整数，通过最高位区分中断和异常。进入 `interrupt_handler()` 后，仍需去掉表示中断的最高位，再按 `IRQ_*` 编号处理。源码中的表达式为：

```c
intptr_t cause = (tf->cause << 1) >> 1;
```

`tf->cause` 的类型是无符号的 `uintptr_t`，因此这里先进行无符号移位、清除最高位，再把结果交给 `cause`。这一点需要结合字段类型看，不能只看最后接收变量的类型。

我们将两类处理的规格整理为：

| 处理入口 | 前置状态 | 返回前应满足的状态 |
|---|---|---|
| `interrupt_handler()` | `tf` 指向已保存的现场，中断类型已经由分派函数确认 | 按类型处理；时钟事件重新安排、计数正确；不因普通时钟中断而推进 `epc` |
| `exception_handler()` | `tf->cause` 为异常编号，目标指令位于本实验可读的内核地址范围 | 对断点和非法指令输出信息并跳过对应指令；其他异常输出现场 |
| `trap_insn_len()` | `epc` 处的指令半字可读取 | 对本实验出现的 16 位、32 位指令返回对应长度 |

#### 4.3.2 时钟中断：设置一个时刻，怎样变成持续事件

沿着 `clock_init()` 往下看，`sbi_set_timer()` 接收的是一个到期时刻。`clock_set_next_event()` 只是把当前 `time` 加上 `timebase` 后提交给 OpenSBI，不会自动替我们安排所有后续事件。

因此，中断处理中的顺序是：

```c
clock_set_next_event();
if (++ticks % TICK_NUM == 0) {
    print_ticks();
    if (++num_prints == SHUTDOWN_AFTER) {
        sbi_shutdown();
    }
}
```

先重设未来的到期时刻，再计数和输出。只设置第一次事件，不能形成我们需要的周期；到期后如果不妥善处理挂起状态，也可能反复进入中断处理，而不是按期产生新的节拍。`ticks` 必须按实际收到的时钟中断逐次增加。

本环境的 `time` 计数器频率为 10 MHz，`timebase` 为 100000，因此目标间隔约为 10 ms，每 100 次中断打印一行。这里读的是 `time`，不能把它简单等同于 CPU 执行指令的周期计数。中断延迟和模拟器运行状况也会影响实际经过的时间，所以“约每秒一行”不等于严格的秒表。

指导书提出累计输出后关机，但当前框架没有给出 `SHUTDOWN_AFTER` 的取值。实现将它定义为 10，即累计 1000 次时钟中断后请求关机。这个取值是小组在当前实现中的选择。评分用例在 `ticks` 达到 200 后输出通过标记，早于关机阈值。

`volatile` 使主流程对 `ticks` 的读取不会被当作不变值缓存，但它不提供多核互斥，也不使 `ticks++` 自动成为跨核原子操作。本实验的单核中断处理条件与这套用法相匹配。

#### 4.3.3 异常返回：要不要改地址，改多少

非法指令和断点异常中，处理函数调整的是 `tf->epc`，之后由模块一写回 `sepc`。两个函数不需要各自执行 `sret`。本实验选择在输出信息后跳过触发异常的指令，因此若不修改地址，返回后会再次触发同一异常。

跳过的长度必须从实际编码判断。成员提交的反汇编记录中，断点使用 `9002`，即 2 字节的压缩断点；非法指令 `.word 0x0000007b` 占 4 字节。若两者统一加 4，就会跳过断点之后本应执行的内容；下一条指令若是 4 字节，还可能落在其内部。

当前辅助函数为：

```c
static size_t trap_insn_len(uintptr_t epc) {
    uint16_t low = *(const uint16_t *)epc;
    return ((low & 0x3) == 0x3) ? 4 : 2;
}
```

先读 16 位，使读取与本实验可能出现的 2 字节指令对齐条件相符。这一实现覆盖本次使用的 16 位和 32 位编码；最低两位为 `11` 也可能是更长编码的前缀，所以它不是通用的 RISC-V 指令长度解码器。直接读取 `epc` 也以对应内核地址可读为前提，不能直接扩展为对任意用户地址的安全访问。

对未要求恢复的异常，代码只调用 `print_trapframe()`，不修改 `epc`。这提供诊断信息，不代表已经修复该异常；若原指令再次执行仍会出错，就仍可能再次陷入。

## 六、总结与收获

### 6.1 这次实验中形成的理解

**第一，硬件进入 Trap，不等于软件现场已经全部保存。** 硬件提供原因和返回状态，汇编仍需把通用寄存器放到一个确定的布局中。只有保存代码和 `struct trapframe` 一致，C 函数收到的字段才有意义。入口与恢复之间任何一个偏移错误，都可能在返回后才表现出来。

**第二，返回地址是处理策略的一部分。** 本实验的断点和非法指令选择跳过原指令，所以要修改 `epc`。如果以后实现可恢复的缺页异常，处理完成后通常应重试原指令。不能把本次的“增加偏移”推广为所有异常的统一做法。

**第三，持续时钟中断依赖软件参与。** 框架提供的是设置未来到期时刻的接口，周期来自处理函数不断重设。`ticks` 的增长说明事件被处理，并不意味着内核已经进行时间片调度。

**第四，原样迁移算法也需要重新检查环境。** `page_init()` 的主要逻辑沿用 Lab2，但地址宏、内核大小和中断保护都与新框架有关。能够复用的单位是满足接口约定的实现，迁移之后仍需检查新的调用关系和运行结果。

### 6.2 与操作系统原理的联系和区别

| 原理中的概念 | 本实验中的对应 | 本实验尚未覆盖的部分 |
|---|---|---|
| 中断向量与事件分派 | `stvec` 指向统一入口，C 层根据原因分派 | 完整的外部设备和中断控制器处理 |
| 上下文保存与恢复 | Trap frame、汇编保存与恢复、`sret` | PCB、就绪队列和切换到另一个进程 |
| 时钟与分时调度 | 定时事件和 `ticks` 计数 | 时间片管理、调度算法和抢占式进程切换 |
| 临界区保护 | 分配器接口保存中断状态、关闭本核可屏蔽中断，再恢复旧状态 | 多核互斥和完整的锁设计 |
| 异常恢复 | 对本实验要求的异常调整返回位置 | 请求调页、页面置换及一般错误恢复 |
| 用户态请求内核服务 | 当前框架为后续工作提供入口基础 | 用户栈到内核栈切换、系统调用分派及返回值约定 |

本实验中，关闭本核中断可以避免本核可屏蔽中断处理与临界区交错，但不能屏蔽同步异常，也不能阻止其他核访问共享数据。当前时钟处理函数本身不操作空闲链表；保留分配器外层的中断保护，是为带中断的内核框架维护接口约束，不能写成实验中已经观察到了链表并发损坏。

### 6.3 使用 AI 时，我们需要自己确定什么

模块一的两轮输入说明，明确的接口和状态约束比笼统要求“写一个中断处理程序”更容易核对。我们需要先确定 Trap frame 的布局、哪些字段允许修改、栈指针何时仍是读取基址，再让生成代码满足这些条件。

对生成结果的检查也不能停在解释是否顺畅。`mv a0, sp` 要对应真实的调用约定，`epc` 的推进要对应实际编码，地址宏要对应当前映射。代码有了明确的检查依据，才能判断它是否符合实验要求。

现有记录中，模块一曾因模块二未完成而无法构建，也遇到工具链的 CSR 名称问题。它们提醒我们保留每轮真实结果：局部代码补齐、单文件编译成功和整合运行通过是三个不同阶段。最终的 100/100 是整合测试证据，不能反过来改写早期记录为“当时已经通过”。
