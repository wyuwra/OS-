## 三、实验整体逻辑分析

### 3.1 实验主线

在 Lab1 完成内核启动和基本输出的基础上，Lab2 重点解决物理内存的探测与动态管理问题。内核启动后首先需要探明可用物理内存的边界，利用 `struct Page` 页描述符数组记录每一页的状态，将固件、内核代码段及页描述符自身占用的内存标记为保留，最后把剩余的完整空闲物理页转交给物理内存分配器。

围绕物理页的分配与回收，实验依次探讨了多种管理策略：通过阅读 First-Fit 源码掌握空闲链表的基本维护，通过实现 Best-Fit 和 Buddy 对比不同选块与合并策略对外部碎片和内部碎片的影响，再通过选做的 SLUB 分配器在页分配器之上构建出细粒度的内核对象管理机制。此外，通过 GDB 跟踪启动页表与 QEMU 的地址翻译过程，将内核虚拟地址的访存路径与底层物理内存管理串联起来，形成完整的内存子系统视图。

### 3.2 实现步骤

1. **物理内存探测与初始化。** 解析 DTB 获取物理内存范围，计算页描述符数组的存放位置并完成初始化，扣留固件、内核镜像及描述符数组占用的物理页，将剩余的可用物理页交付给分配器管理。
2. **分析 First-Fit 并实现 Best-Fit。** 阅读默认的 First-Fit 代码，理清空闲块的双向链表组织、拆分与前后合并逻辑；随后在相同的 `pmm_manager` 接口下实现 Best-Fit 算法，对比两种线性链表策略在选块逻辑上的差异。
3. **实现 Buddy 伙伴分配器并构造完备测试。** 采用按阶（$2^k$ 页）分组的空闲链表组织物理页，利用物理页号异或运算实现快速伙伴定位、逐级拆分与递归合并，并针对未对齐边界、非二次幂请求及碎片的合并恢复编写自检用例。
4. **基于页分配器实现 SLUB 对象分配器。** 在底层按页分配的接口之上，设计固定尺寸类别（Size Classes）的 slab 缓存与大对象直接分配路径，实现按字节粒度的内核内存申请与释放。
5. **使用 GDB 调试页表查询与 TLB 机制。** 内核在进入 C 代码前已由 `entry.S` 启用 Sv39 大页映射。通过双 GDB 联调 QEMU 与 ucore，单步跟踪虚拟地址经过软件 TLB 查询、多级页表遍历最终转化为物理地址的全过程。

## 四、实验内容与实现

### 4.1 功能模块一：物理内存初始化

**负责人：** 2412832-王雅枫

**修改文件：** [kern/mm/pmm.c](../lab2_new/kern/mm/pmm.c)。核心函数：

```c
static void page_init(void);
```

#### 4.1.1 地址和页描述符的含义

| 对象 | 含义 | 当前框架的关系 |
|---|---|---|
| VA | 内核使用的虚拟地址 | 直接映射区内 $\text{VA} = \text{PA} + \text{va\_pa\_offset}$ |
| PA | 物理字节地址 | `PADDR(VA)` 从内核直接映射地址减去偏移 |
| PPN | 绝对物理页号 | $\text{PA} \gg \text{PGSHIFT}$ |
| `nbase` | DRAM 起始页号 | $0\text{x}80000000 / 4096 = 0\text{x}80000$ |
| `npage` | 管理结束位置的绝对页号，不包含该页 | 默认 $128\text{ MiB}$ 时为 $0\text{x}88000$ |
| `pages` | 页描述符数组的内核虚拟地址 | 描述符数量是 $\text{npage} - \text{nbase}$ |
| `pages[i]` | 第 $i$ 个描述符 | 对应 PA $(\text{nbase} + i) \times \text{PGSIZE}$ |

需要注意的是，`npage` 是物理页号的上界而非描述符总数；`struct Page *` 指向的是管理元数据本身，不能直接当作所描述物理页的起始地址使用。

#### 4.1.2 行为规格

| 类别 | 约束 |
|---|---|
| 前置条件 | 启动页表和内核栈已就绪，DTB 已完成解析，当前分配器的 `init()` 已调用；采用单段连续 RAM 与固定内核映射布局 |
| 成功后置条件 | 虚拟物理偏移、页号上界、描述符数组地址设置正确；全部描述符先初始化为保留状态；仅将元数据末尾之后的完整空闲页交付给分配器 |
| 错误处理 | DTB 信息无效、地址范围计算溢出、RAM 无法容纳内核或描述符数组、扣除后无完整空闲页时，直接触发 `panic` |
| 接口约束 | 调用 `init_memmap(base, n)` 时保证 $n > 0$；传入的描述符范围有效，且交付前每一页均处于保留状态 |
| 不变量 | 先完成容量与边界检查再写入描述符数组；不释放内核和元数据占用的物理页；动态使用 `sizeof(struct Page)` 计算大小 |

#### 4.1.3 布局计算与实现顺序

设 DTB 报告的内存起点为 $B$、大小为 $S$，页大小 $P = \text{PGSIZE}$：

```text
raw_end          = B + S                  （先检查加法溢出）
managed_end      = ROUNDDOWN(min(raw_end, PHYSICAL_MEMORY_END), P)
descriptor_count = PPN(managed_end) - nbase
pages_va         = ROUNDUP(end, P)
pages_pa         = PADDR(pages_va)
descriptor_bytes = descriptor_count * sizeof(struct Page)
metadata_end     = pages_pa + descriptor_bytes
free_begin       = ROUNDUP(metadata_end, P)
free_count       = (managed_end - free_begin) / P
```

所有内存区间均采用**左闭右开**表示法，结束地址不包含在区间内。

具体实现分为以下六步：

1. **读取并校验 RAM 范围。** 先设置 `va_pa_offset` 再使用 `PADDR` 宏；若起点或大小为零，或者起点加大小发生无符号溢出，立即触发 `panic`。
2. **确定管理上界。** 将管理末尾限制在框架上限 `0x88000000` 以内，并向下按页对齐。同时检查该范围能否完整覆盖内核起始地址与链接符号 `end`。
3. **安置页描述符数组。** 将 `pages` 数组放在内核结束符号 `end` 之后的首个页对齐位置，使用 `sizeof(struct Page)` 计算总字节数。
4. **先检查容量，后写入内存。** 在对齐和乘法运算前检查溢出风险，确认扣除描述符占用后至少还剩一页完整空闲内存，随后再开始初始化描述符数组。
5. **全部标记为保留。** 遍历描述符数组，清零引用计数、标志位和 `property` 字段，初始化链表节点，并统一设置 `PG_reserved` 标志，防止已用内存被误分配。
6. **交付完整空闲页。** 将描述符数组的结束地址向上按页对齐得到 `free_begin`，调用 `init_memmap(pa2page(free_begin), free_count)` 将剩余物理页移交分配器，由分配器清除这些页的保留位并建立空闲链表。

物理内存的整体划分如下图所示（描述符数组覆盖整个管理范围，其自身也存放在这段 RAM 中）：

```text
0x80000000          0x80200000        pages_pa          free_begin        managed_end
    | 固件预留区域       | 内核、栈、页表等 | 页描述符及对齐尾部 | 可分配完整页       |
    +------------------+----------------+------------------+------------------+
    |<-------------------- 保留 -------------------------->|<---- 空闲 ------>|
```

注：前 $2\text{ MiB}$ 是实验框架约定的固定预留区间；当前 QEMU 环境下 OpenSBI 固件实际报告自身占用为 $112\text{ KiB}$。

#### 4.1.4 页对齐方向的选择与开销分析

在计算边界时，`managed_end` 采用向下页对齐，是因为末尾不足一页的零头无法作为完整物理页分配；而 `free_begin` 采用向上页对齐，是因为只要某个物理页内还存有半截页描述符，该页就不能开放给分配器写入。一处向下、一处向上，分别避免了越界分配和破坏管理元数据。

页描述符初始化仅在系统启动时执行一次，时间复杂度和空间复杂度均为 $O(\text{npage} - \text{nbase})$。在当前 RV64 构建下，`sizeof(struct Page)` 为 $40$ 字节，默认 $128\text{ MiB}$ 内存共需 $32768$ 个描述符，占用 $1310720$ 字节。

#### 4.1.7 模块一 Challenge：硬件可用物理内存范围的获取方法（思考题）

**负责人：** 2412832-王雅枫

**题目要求：** 当操作系统无法提前写死目标机器的物理内存范围时，如何在启动阶段动态获取可用物理内存区间？（参考[课程模块一要求](http://oslab.mobisys.top/lab2026/_book/lab2/lab2_2_1_exercise.html)）

**分析与解答：** 操作系统在启动时应当通过硬件平台的启动协议，接收由固件（Firmware）或引导程序（Bootloader）传递的物理内存布局描述。不同架构与固件环境下的主流获取方式对比如下：

| 方法 | 获取的信息内容 | 适用环境与注意事项 |
|---|---|---|
| 设备树（DTB） | `/memory` 节点的 `reg` 属性记录一段或多段 RAM 的起始地址与长度；需结合保留内存节点排除不可用区域 | RISC-V 与嵌入式 Linux 常用（本实验采用此方式）。解析时需遵守 `#address-cells` 和 `#size-cells` 规范，不能写死为单段 64 位整数 |
| UEFI 内存映射 | 引导阶段调用 Boot Services 的 `GetMemoryMap()` 获取带类型的内存描述符数组并传给内核 | 支持 UEFI 的现代平台。需严格遵循 `ExitBootServices()` 的调用时序，按描述符类型区分可用 RAM、ACPI 表与运行时保留区 |
| BIOS E820 | 实模式下通过 `INT 15h, AX=E820h` 中断逐条查询物理地址区间及其可用状态 | 传统 x86 PC BIOS 环境。仅限在进入保护模式/长模式前的引导阶段调用，不适用于当前 RISC-V 环境 |
| 平台专用寄存器 | 在掌握芯片手册的前提下，直接读取内存控制器（DRAM Controller）配置与 SoC 地址映射表 | 强依赖具体 SoC 硬件。即便读出总容量，仍需配合固件预留信息和外设空洞分布才能算出安全的可分配区间 |

相关规范定义可参考 [Devicetree 节点规范](https://devicetree-specification.readthedocs.io/en/latest/chapter3-devicenodes.html#memory-node)、[UEFI 内存分配服务](https://uefi.org/specs/UEFI/2.10/07_Services_Boot_Services.html#memory-allocation-services) 以及 [ACPI E820 接口说明](https://uefi.org/specs/ACPI/6.6/15_System_Address_Map_Interfaces.html#int-15h-e820h-query-system-address-map)。

**本实验的代码路径：** 在 ucore 启动时，`entry.S` 将 OpenSBI 通过 `a1` 寄存器传入的 DTB 物理地址保存下来；随后 `dtb_init()` 解析设备树，提取出 RAM 的起始地址和大小；`page_init()` 再通过 `get_memory_base()` 和 `get_memory_size()` 获取这两个值并计算管理边界。当修改 QEMU 的 `-m` 参数时，DTB 内容随之改变，内核无需重新编译即可适应新的内存大小（受限于框架宏 `PHYSICAL_MEMORY_END` 以及当前简化解析器仅读取首段内存的实现）。

**从“获取到 RAM 区间”到“交付给页分配器”的完整处理流程：**

```text
获取固件提供的原始内存区间列表
  → 校验零长度、整数溢出、区间重叠，并按内核支持的最大物理地址截断
  → 筛选出类型为可用 RAM 的区间
  → 挖去固件驻留区、内核代码与数据段、启动栈、初始页表、页描述符数组以及尚未解析完的 DTB 自身
  → 将剩余的每一段可用区间起点向上页对齐、终点向下页对齐
  → 逐段调用 init_memmap 交付给物理页分配器，严禁跨越中间的保留空洞将不同区间强行连成一整块
```

在标准设备树规范中，除了 `/memory` 节点外，还需要解析 `/reserved-memory` 节点与文件头部的 Memory Reservation Block（参考 [DTB 保留块规范](https://devicetree-specification.readthedocs.io/en/v0.2/flattened-format.html#memory-reservation-block)）。例如，若可用 RAM 为 `[0x80000000, 0x88000000)`，扣除内核与描述符后起点为 `free_begin`，而中间 `[0x84000000, 0x84200000)` 被标记为保留空洞，则初始化代码应当将 `[free_begin, 0x84000000)` 和 `[0x84200000, 0x88000000)` 作为两段独立的连续区域分别调用 `init_memmap`，同时让空洞对应的页描述符继续保持 `PG_reserved` 状态。

**补充讨论：能否通过 `satp` 页表或直接读写内存来探测容量？**
- **不能通过 `satp` 或页表反推。** 页表仅定义虚拟地址到物理地址的映射关系与访问权限，并不代表目标物理地址上真的插有内存条。例如本实验 `entry.S` 使用一个根页表大页项直接映射了 $1\text{ GiB}$ 地址空间，但默认物理内存只有 $128\text{ MiB}$。
- **不能在未知地址空间中盲目使用读写试探（Memory Probing）。** 对未知的物理地址执行写操作，极易误触外设的 MMIO 寄存器导致硬件状态错乱，或者覆盖正在运行的固件与内核数据，也可能触发总线访问异常（Load/Store Access Fault）或遇到地址回绕（Address Aliasing）。因此，操作系统必须依赖固件传递的内存映射表，而不能靠暴力试写来探测可用内存。

### 4.2 功能模块二：物理内存分配

#### 4.2.1 任务一：First-Fit 分析

**负责人：** 2413276-胡楚骅

**（1）空闲页初始化**

First-Fit 分配器首先在 `default_init()` 中初始化空闲块双向循环链表 `free_list`，并将空闲页总数 `nr_free` 置零。

当 `page_init()` 调用 `default_init_memmap(base, n)` 交付一段连续物理页时，函数先断言 $n > 0$，随后遍历这 $n$ 个页描述符：确认每一页原先处于保留状态，清除其标志位与 `property` 字段，并将引用计数清零。接着，将起始页 `base` 的 `property` 设为 $n$ 并打上 `PG_property` 标志，表示这是一个包含 $n$ 页的空闲块首页，同时将 `nr_free` 增加 $n$。最后，按照物理地址递增的顺序，将 `base->page_link` 插入到 `free_list` 的对应位置。

**（2）分配连续物理页**

`default_alloc_pages(n)` 首先断言 $n > 0$；若申请页数 $n > \text{nr\_free}$，直接返回 `NULL`。随后从 `free_list` 表头开始顺序遍历各空闲块首页，寻找第一个满足 `page->property >= n` 的块。

找到目标块后，先将其从链表中取下。若该块页数大于 $n$，则发生拆分：将跳过前 $n$ 页后的新起点 `page + n` 设为剩余空闲块的首页，写入剩余页数 `page->property - n` 并设置 `PG_property` 标志，再插回原链表位置。最后，将 `nr_free` 减去 $n$，清除所分配块首页 `page` 的 `PG_property` 标志并返回 `page`。若遍历完整个链表仍未找到足够大的块，则返回 `NULL`。

**（3）回收页面与合并相邻空闲块**

`default_free_pages(base, n)` 首先断言 $n > 0$，并逐页检查归还区间内的页面既不是保留页，也不是已处于空闲链表中的块首页。随后重置这 $n$ 页的标志位与引用计数，将首页 `base` 的 `property` 设为 $n$、置上 `PG_property` 标志，并将 `nr_free` 增加 $n$。接着按地址递增顺序将 `base` 插入 `free_list`。

插入完成后，立即检查与前后相邻空闲块的合并条件：
- **向前合并：** 检查链表中的前驱节点 `p`。若 `p + p->property == base`，说明前一个空闲块与当前块在物理上紧挨着。此时将 `base->property` 累加到 `p->property` 上，清除 `base` 的 `PG_property` 标志并从链表中删除 `base`，最后令 `base = p`。
- **向后合并：** 以更新后的 `base` 检查后继节点 `p`。若 `base + base->property == p`，说明当前块与后一个空闲块物理连续。同样将 `p->property` 累加到 `base->property`，清除 `p` 的首页标志并将其从链表中摘除。

**（4）First-Fit 算法的优缺点与改进方向**

First-Fit 每次从低地址开始寻找第一个满足要求的空闲块，实现简单，且倾向于将高地址的大块内存保留下来。但缺点在于低地址区域容易被反复切割，留下许多难以被后续请求利用的外部小碎片；同时每次分配都从头扫描这些小碎片，拉低了查找效率。

针对这些问题，可以从两个方向改进：
- **调整选块策略：** 例如改用 Best-Fit 选择最接近申请大小的块以大块保留，或采用 Next-Fit 从上一次分配结束的位置继续扫描以分散碎片并减少头部遍历次数。
- **优化数据结构：** 引入按块大小分桶的多条空闲链表（Segregated Free Lists）或平衡二叉树，避免在单条线性链表上进行 $O(k)$ 复杂度的顺序查找，更彻底的做法则是采用按二次幂分阶管理的 Buddy System。

**（3）Best-Fit 算法的优缺点与改进空间**

Best-Fit 每次挑选最接近请求大小的空闲块，避免了轻易拆散大块连续内存。但它在未遇到精确匹配块时必须扫描整条空闲链表，时间复杂度为 $O(k)$（$k$ 为空闲块数量）；而且由于每次都挑最接近的块切割，剩余部分往往是非常零碎的微小块（如 1 页），长期运行后链表中容易堆积大量难以利用的微小外部碎片。

若要优化查找开销，可以使用以`(property, address)`为键值的红黑树或跳表替代单向顺序扫描，将查找复杂度降至 $O(\log k)$；或者针对单页、双页等高频请求单独设立快速缓存链表（类似伙伴系统或分级空闲链表），减少遍历整条链表的次数。

#### 4.2.3 任务三：Buddy System 实现

**负责人：** 2412737-罗元伟

本小节实现 Buddy System（伙伴系统）连续物理页分配器。算法通过按阶（Order）组织的空闲链表管理内存，每个块的大小固定为 $2^k$ 页，分配时由高阶向低阶逐级对半拆分，释放时通过异或运算快速定位伙伴块并递归向上合并。

**（1）接口与内部状态**

新增 [`buddy_pmm.c`](../lab2_new/kern/mm/buddy_pmm.c) 和 [`buddy_pmm.h`](../lab2_new/kern/mm/buddy_pmm.h)，并在 `pmm.c:init_pmm_manager()` 中接入 `buddy_pmm_manager`。核心函数职责如下：

| 函数 | 职责 |
|---|---|
| `buddy_init()` | 初始化各阶空闲链表、空闲页总计数和最大阶数 |
| `buddy_init_memmap(base, n)` | 接收 `page_init()` 交付的可用页，按物理页号对齐关系拆分为若干 $2^k$ 大小的块并登记 |
| `buddy_alloc_pages(n)` | 将申请页数向上取整到 $2^k$，查找最小可用阶并逐级拆分，记录分配元数据 |
| `buddy_free_pages(base, n)` | 校验分配记录，归还整个 $2^k$ 页块并递归向上合并空闲伙伴 |
| `buddy_nr_free_pages()` | 返回当前实际未分配的空闲物理页总数 |
| `buddy_check()` | 在受控隔离区域内执行九组完备性自检，结束后恢复真实分配器状态 |

阶数为 $k$ 的块包含 $2^k$ 个连续物理页。对于空闲块的首页，置上 `PG_property` 标志，用 `property` 字段记录阶数 $k$，并通过 `page_link` 挂入第 $k$ 阶空闲链表；对于已分配块的首页，利用 `flags` 的 bit 2 标记已分配状态，在 `flags` 高位记录原始请求页数 $n$，`property` 仍保存实际分配阶数 $k$。块内其余非首页的 `flags` 和 `property` 均保持为零。

在计算对齐与伙伴关系时，统一使用绝对物理页号 $\text{PPN} = \text{page2ppn(page)}$，避免错误地对虚拟地址、描述符指针或数组下标做异或运算。

**（2）初始化、拆分与合并逻辑**

在 `buddy_init_memmap(base, n)` 中，由于传入的起始物理页号不一定按大块对齐，且总页数 $n$ 也不一定是 $2$ 的幂，函数从起始 PPN 开始循环：每一步挑选满足“起始 PPN 能被 $2^k$ 整除，且 $2^k \le \text{剩余页数}$”的最大阶数 $k$，将该块登记并尝试与已有伙伴合并，直到 $n$ 页全部登记完毕。这种贪心切分方式保证了任意起点和长度的连续内存都能被精确纳入管理，既不遗漏尾部页面，也不会越过未交付的内存空洞。

分配 $n$ 页时，先向上取整找到满足 $2^k \ge n$ 的最小阶 $k$。若第 $k$ 阶链表非空则直接摘下首块；否则向更高阶查找第一个非空阶 $j (j > k)$，取下块后循环执行对半拆分：每次将高地址的右半块插入第 $j-1$ 阶空闲链表，保留低地址的左半块继续拆分，直至降到目标阶 $k$。随后将总空闲页数 `nr_free` 减去实际占用的 $2^k$ 页（例如申请 3 页实际占用并扣减 4 页，申请 5 页实际占用并扣减 8 页）。

释放时，调用者传入分配时的返回指针 `base` 和原始申请页数 $n$（如 `free_pages(p, 3)`）。函数校验 `base` 记录的原始请求页数与 $n$ 一致后，读出实际分配阶数 $k$，按 $2^k$ 页恢复空闲计数，并按以下公式计算伙伴块的首页物理页号：

$$\text{buddy\_ppn} = \text{ppn} \oplus (1 \ll \text{order})$$

当且仅当该伙伴页号落在有效管理范围内、对应页面非保留、处于空闲状态（`PageProperty` 为真）且阶数同样为 $\text{order}$ 时，才将伙伴从链表摘下，取两者中的较低地址作为新首页，令 $\text{order} \leftarrow \text{order} + 1$，继续向更高阶尝试合并。需要注意的是，物理地址相邻的两个同阶块若不属于同一个 $2^{\text{order}+1}$ 对齐的父块，它们的页号异或结果并不匹配，绝不能合并。

### 4.3 模块二 Challenge：SLUB（选做）

**负责人：** 2412737-罗元伟

在页分配器之上，我们进一步设计并实现了简化的 SLUB 内核对象分配器，提供按字节粒度的内存申请与释放接口。底层直接调用 `alloc_pages()` 和 `free_pages()` 获取或归还物理页，上层则通过尺寸类别（Size Classes）和页内空闲链表管理小对象。

**（1）接口与内存布局**

新增 [`slub.c`](../lab2_new/kern/mm/slub.c) 和 [`slub.h`](../lab2_new/kern/mm/slub.h)，对外提供三个核心函数：

```c
void slub_init(void);
void *slub_alloc(size_t size);
void slub_free(void *ptr);
```

`slub_init()` 在 `pmm_init()` 完成后调用。`slub_alloc(size)` 返回至少 `size` 字节、满足 16 字节对齐的内核直接映射虚拟地址；当 `size == 0`、计算溢出或底层物理页不足时返回 `NULL`。`slub_free(NULL)` 直接返回，传入有效对象指针时将其归还至所属 slab 或底层页分配器。

对于 $\le 2048$ 字节的小对象，设立 8 个2的幂次尺寸类别，向上取整匹配最小可用类别。每个小对象 slab 占用 1 个物理页（$4096$ 字节），页首放置 56 字节的 `slub_header` 并填充对齐至 64 字节，剩余 $4032$ 字节划分为等长的对象槽位：

| 类别字节数 | 16 | 32 | 64 | 128 | 256 | 512 | 1024 | 2048 |
|---|---|---|---|---|---|---|---|---|
| 单页容量 | 252 | 126 | 63 | 31 | 15 | 7 | 3 | 1 |

```text
小对象页：[页头与对齐填充，64字节][等长槽位...][尾部余量]
大对象块：[首页头部，64字节][至少 size 字节用户区间][余量]
```

因此单页实际对象容量为 $(4096 - 64) / \text{object\_size}$。空闲槽位利用自身前 8 字节存放单向链表 `next` 指针；槽位分配给调用者后，分配器不再读取其内部数据，调用者可以安全覆写整个请求区间。

**（2）缓存状态流转与大对象处理**

每个尺寸类别维护一个静态的 `slub_cache` 结构，包含 `partial`（部分占用）和 `full`（已满）两条双向链表。页首的 `slub_header` 记录所属 `cache` 指针、总容量、当前在用对象数 `inuse`、空闲槽位链表头 `freelist` 以及挂载到缓存链表的节点。
- **小对象分配与释放：** 优先从对应类别的 `partial` 链表首部 slab 弹出一个空闲槽位；若 `partial` 为空，则调用 `alloc_pages(1)` 申请新页并初始化为 slab。分配后若 `inuse == capacity`，将该 slab 从 `partial` 移入 `full`。释放时，若该 slab 原先处于 `full` 则移回 `partial`；若释放后 `inuse` 降为 0，则先将其从 `partial` 链表摘除，再立即调用 `free_pages(page, 1)` 将整页归还底层。
- **大对象直接分配：** 对于 $> 2048$ 字节的请求，计算所需页数 $p = \lceil (\text{size} + 64) / 4096 \rceil$，直接调用 `alloc_pages(p)`。在返回块的首页头部设置 `cache = NULL` 并记录原始请求页数 `requested_pages = p`，返回偏移 64 字节后的首地址。
- **指针逆向定位与 Buddy 兼容：** 无论是小对象槽位还是大对象起始地址，它们与各自的 `slub_header` 都位于同一个物理页（大对象的首页）内。因此 `slub_free(ptr)` 只需执行 `ROUNDDOWN(ptr, PGSIZE)` 即可直接拿到 `slub_header` 指针，完全不占用底层 `struct Page` 的 `property` 或 `flags` 字段。由于底层 Buddy 分配器会将非二次幂页数向上取整（如大对象请求 3 页实际分配 4 页），但要求释放时传入原始请求页数，因此大对象释放时读取 `header->requested_pages` 传给 `free_pages()`，实现了两层分配器的无缝衔接。

**（3）提示词设计与迭代过程**

同样分为实现与测试两轮进行：第一轮完成 SLUB 分配器代码与内核初始化接入；第二轮编写独立的 [`slub_test.c`](../lab2_new/kern/mm/slub_test.c) 测试套件。

#### 4.4.3 satp 寄存器、根页表与大页叶子项解析

单步进入 `get_physical_address` 函数后，打印 `env->satp` 的值为 `0x800000000008020a`：最高 4 位 $\text{MODE} = 8$ 表示启用 Sv39 三级页表机制；低 44 位 $\text{PPN} = 0\text{x}8020\text{a}$，左移 12 位得到根页表的物理基地址 $\text{base} = 0\text{x}8020\text{a}000$。此时 CPU 处于 S 模式（`mmu_idx == 1`），既不走 M 模式的直接物理访问分支，也不走 Bare 分支，而是初始化 Sv39 参数：`levels = 3`、`ptidxbits = 9`、`ptesize = 8`。

![Sv39 模式与根页表物理地址](images/mmu-02-satp-root.png)

执行 `until cpu_helper.c:252` 来到页表项（PTE）读取位置，单步执行后观察第一轮循环（$i = 0$，即根页表级）的各变量值：

| 变量 | 实际值 | 含义解析 |
|---|---|---|
| `i` | `0` | 第 0 轮循环，查询顶级（根）页表 |
| `idx` | `0x1ff` | 虚拟地址 `0xffffffffc0200404` 的 $\text{VPN}[2]$（位 38:30）为 $511$ |
| `pte_addr` | `0x8020aff8` | 页表项物理地址 $= 0\text{x}8020\text{a}000 + 511 \times 8$ |
| `pte` | `0x200000cf` | 低 8 位标志为 `0xcf`，即 V、R、W、X、A、D 位均为 1，U 位为 0 |
| `ppn` | `0x80000` | $\text{pte} \gg 10$，对应物理基址 $0\text{x}80000000$ |

在 `cpu_helper.c` 中，第 256 行检查有效位 `V == 1`；第 259 行判断 `R/W/X` 是否全为 0（若全为 0 则是通往下一级页表的中间节点指针，否则为当前级别的叶子页表项）。由于 `entry.S` 中预设的该表项 `R/W/X` 均为 1，代码直接跳过中间节点分支进入第 262 行的叶子项权限与大页对齐检查。这直观展示了 Sv39 的 $1\text{ GiB}$ 大页（Gigapage）机制：虽然 Sv39 最多支持三级页表，但遇到根级叶子项时只需一次内存读取即可完成转换。

![实际读取根页表第 511 项与提取物理页号](images/mmu-03-page-table-entry.png)

#### 4.4.4 1 GiB 大页的物理地址合成与权限检查

通过 S 模式权限与大页低位对齐检查后，由于该 PTE 的 A（Accessed）和 D（Dirty）位已在汇编中预先置 1，无需执行原子写回更新。随后代码来到第 333–334 行合成最终转换出的物理页基址：

```c
target_ulong vpn = addr >> PGSHIFT;
*physical = (ppn | (vpn & ((1L << ptshift) - 1))) << PGSHIFT;
```

此时 `ptshift = 18`（因为第 0 级叶子项跨越了底下两级共 $9 + 9 = 18$ 位页号），`vpn = 0xffffffffc0200`。上式将 PTE 提供的 `ppn` 高位（`0x80000`）与虚拟页号 `vpn` 的低 18 位（`0x00200`）按位或，再左移 12 位，计算出当前访问所在的 **$4\text{ KiB}$ 物理页基址** `*physical = 0x80200000`。加上页内偏移 `0x404` 后，对应的完整物理字节地址即为 `0x80200404`。

![大页映射下的页基址与完整物理地址](images/mmu-04-physical-address.png)

执行 `finish` 返回到 `riscv_cpu_tlb_fill` 的第 472 行，可见返回值 `ret = 0`（转换成功），导出权限 `prot = 7`（可读、可写、可执行），并顺利通过 PMP（物理内存保护）检查准备填入软件 TLB。

#### 4.4.5 软件 TLB 的填充、重查找与后续命中

单步进入 `tlb_set_page`，观察到传入参数为虚拟页基址 `vaddr_page = 0xffffffffc0200000`、物理页基址 `paddr_page = 0x80200000` 以及缓存粒度 `size = 0x1000`（$4096$ 字节）。可以看到，尽管硬件页表项是一个 $1\text{ GiB}$ 的大页，QEMU 的软件 TLB 依然按 $4\text{ KiB}$ 标准页粒度来建立缓存条目（并在内部计算出客体虚拟地址到宿主机模拟内存的偏移量 `addend`）。

![软件 TLB 的映射页与 4096 字节填充大小](images/mmu-05-tlb-fill.png)

填充完毕返回 `get_page_addr_code` 后，第 1033–1034 行重新计算 TLB 索引并获取条目指针 `entry`（因为 `tlb_fill` 过程中软件 TLB 数组可能发生动态扩容重分配，旧指针可能失效），并在第 1036 行通过断言确认新填入的条目已经处于命中状态。（注：截图中曾误将源码里的 `assert(...)` 当作 GDB 命令敲入，提示 `Undefined command`，随后输入 `next` 正常执行了 C 代码中的断言并来到第 1039 行。）

#### 4.4.6 数据写入（Store）的地址翻译观察

禁用取指断点后，为观察内核数据访存的翻译过程，在宿主 GDB 中针对内核高地址空间的写操作设置条件断点：

```gdb
break riscv_cpu_tlb_fill if access_type == MMU_DATA_STORE && mmu_idx == 1 && address >= 0xffffffffc0000000ULL
```

断点命中时，捕获到一次 8 字节的数据写入（`MMU_DATA_STORE`，`size = 8`），目标虚拟地址为 `0xffffffffc0209ff8`。经过 `get_physical_address` 转换后返回 `ret = 0`，对应的 $4\text{ KiB}$ 物理页基址为 `0x80209000`，加上页内偏移 `0xff8` 得到实际物理地址 `0x80209ff8`。

对照内核反汇编代码可知，`kern_init` 入口处 `0xffffffffc0200414` 指令为 `addi sp, sp, -16`，紧接着 `0xffffffffc020041a` 为保存返回地址的压栈指令 `sd ra, 8(sp)`。由于初始内核栈顶 `bootstacktop` 位于 `0xffffffffc020a000`，计算 $\text{bootstacktop} - 16 + 8$ 恰好等于 `0xffffffffc0209ff8`，验证了这次数据写入正是 `kern_init` 函数序言中的首次压栈操作。

#### 4.4.7 Bare 模式对比与 QEMU 软件 TLB 的作用机制

最后对比未开启分页（Bare 模式）时的地址转换路径。最初尝试在内核 GDB 中使用 `monitor system_reset` 热复位系统，但发现复位后客体 PC 停留在 OpenSBI 异常入口 `0x80000474` 未能正常重走引导流程；于是改用 `monitor quit` 彻底关闭模拟器，重新启动三终端会话并在宿主 GDB 中设置断点：

```gdb
break cpu_helper.c:197 if mmu_idx == 1 && (env->satp >> 60) == 0
```

当 OpenSBI 刚刚切换到 S 模式跳转到内核入口 `0x80200000`、尚未执行 `entry.S` 中写 `satp` 开启分页的指令时，断点成功命中。此时 `mmu_idx = 1`（S 模式），`env->satp = 0x0`（$\text{MODE} = 0$，即 Bare 模式）。单步执行第 197 行 `*physical = addr` 后，物理地址直接被赋值为输入地址 `0x80200000` 并返回，没有发生任何页表内存读取。

![全新启动后的 S 模式 Bare 直接映射与调用栈](images/mmu-09-bare-mode.png)

值得注意的是，观察上图的调用栈可以发现，即便在 Bare 模式下，QEMU 依然经历了 `get_page_addr_code → tlb_fill → riscv_cpu_tlb_fill → get_physical_address` 这条软件 TLB 填充链路。这是因为真实硬件 CPU 的 TLB 只负责缓存虚拟页号到物理页号的页表翻译结果；而 QEMU 作为跨架构全系统模拟器，其内部的“软件 TLB”不仅缓存客体虚拟地址到客体物理地址的转换，更核心的作用是缓存**客体虚拟地址到宿主机进程虚拟地址的偏移量（`addend`）**以及该页属于普通 RAM 还是外设 MMIO 的访问权限分类。因此，哪怕客体处于不开启分页的 Bare 模式，首次访问某个 $4\text{ KiB}$ 页面时依然会触发 QEMU 的软件 `tlb_fill` 慢路径来建立宿主内存映射缓存。

### 5.5 模块一 GDB 交付状态核验

为直接观察 `page_init()` 将物理页移交给分配器前后的状态变化，我们使用 GDB 脚本（[commands.gdb](evidence/module1-gdb/commands.gdb)）在关键函数入口设置断点并打印内存结构：

```gdb
set pagination off
set architecture riscv:rv64
file bin/kernel
target remote 127.0.0.1:<本次端口>
break page_init
continue
bt 3
break *default_init_memmap
continue
set $base = (struct Page *)$a0
set $count = (unsigned long)$a1
p/x nbase
p/x npage
p/x pages
p *$base
delete breakpoints
tbreak *default_check
continue
p free_area.nr_free
p *$base
finish
p free_area.nr_free
detach
quit
```

1. **在 `page_init` 入口：** 打印调用栈确认为 `kern_init → pmm_init → page_init`。
2. **在 `default_init_memmap` 首条指令处（交付前瞬间）：** 通过寄存器 `$a0` 和 `$a1` 获取即将交付的起始描述符 `$base` 与页数 `$count`（$31929$）。抽查 DRAM 起始页、元数据末尾页、首个待交付空闲页 `$base` 以及管理末页，确认其 `flags` 均为 `1`（`PG_reserved`），`ref = 0`、`property = 0`，链表指针自环。
3. **在 `default_check` 入口处（登记完成后）：** 观察到 `free_area.nr_free` 已变为 $31929$；`$base` 的 `flags` 变为 `2`（保留位已清除，`PG_property` 置位），`property = 31929`；而 `$base` 前一页（元数据尾页）依然保持 `flags = 1` 的保留状态。
4. **执行 `finish` 跑完 `default_check`：** 确认自检结束后 `nr_free` 恢复为 $31929$，断开 GDB 后串口打印 `check_alloc_page() succeeded!`。

## 六、实验总结与收获

### 6.1 对操作系统物理内存管理的理解

| 核心概念 | 本实验中的具体体现 | 关键认识与易错点 |
|---|---|---|
| 物理页帧与描述符 | 以 $4\text{ KiB}$ 为粒度建立 `struct Page` 数组 | `Page *` 是管理元数据的虚拟地址而非物理页本身；`npage` 是绝对页号上界，描述符总数为 `npage - nbase` |
| 元数据空间扣除与对齐 | `pages` 数组置于内核 `end` 之后，SLUB 页头置于页首前 64 字节 | 物理内存末尾需向下页对齐以丢弃残页，元数据末尾需向上页对齐以保护管理结构不被当作空闲页分配 |
| 安全的初始化顺序 | 先校验范围与溢出，再将全部描述符置为 `PG_reserved`，最后开放空闲区 | 防止在未确认内存边界安全前覆写内核，也防止未交付的空洞或内核占用页参入伙伴合并 |
| 外部碎片与内部碎片 | First-Fit/Best-Fit 精确按页切割；Buddy 按 $2^k$ 页取整，SLUB 按尺寸类别取整 | 线性链表精确切割容易产生外部碎片且查找慢；按二次幂或固定类别取整用可控的内部碎片换取了快速查找与高效合并 |
| 伙伴定位与合并条件 | 使用 $\text{ppn} \oplus (1 \ll \text{order})$ 计算伙伴页号 | 必须对绝对物理页号做异或；物理相邻的两个同阶空闲块若不属于同一个 $2^{\text{order}+1}$ 对齐父块，不能合并 |
| 分层内存管理架构 | 底层 Buddy/Best-Fit 负责连续物理页，上层 SLUB 负责字节级对象 | 两层通过 `alloc_pages`/`free_pages` 解耦；SLUB 将元数据放在页首内联存储，不侵占 `struct Page` 的分配器字段 |
| 页表映射与物理分配的职责边界 | `entry.S` 建立 $1\text{ GiB}$ Sv39 根级大页映射；QEMU 按 $4\text{ KiB}$ 填充软件 TLB | 页表只定义地址转换关系（映射了 $1\text{ GiB}$ 不代表真有 $1\text{ GiB}$ 物理内存）；分配器则负责追踪实际存在的 RAM 哪些已被使用 |

### 6.2 AI 辅助内核开发的实践体会

在本次实验中，我们全程使用结构化提示词驱动 AI 完成代码编写与测试构造，总结出以下几点工程经验：

1. **在提示词中显式固化接口不变量与单位语义。** 操作系统底层代码对地址类型和边界极其敏感。在模块一和 Buddy 的提示词中，我们明确区分了虚拟地址、物理地址、绝对物理页号（PPN）和描述符数组下标，并规定了“申请 $n$ 页向上取整占用 $2^k$ 页，释放时仍传入原始请求页数 $n$”的接口契约。把这些跨模块的约定写进 `[RELY]` 和 `[SPECIFICATION]`，有效避免了 AI 在生成 SLUB 大对象回收代码时出现页数不匹配的错误。
2. **将“功能实现”与“测试构造”拆分为独立的两轮对话。** 如果让 AI 在写完分配器的同时顺手写测试，它很容易顺着刚刚写出的代码逻辑去凑测试断言，导致测试失去捉虫能力。我们将流程拆开：第二轮测试提示词要求 AI 建立独立的页面占用位图、用不同于生产代码的算法推导预期值，并强制在每次操作后扫描全表做结构一致性审计，从而真正检验了拆分、合并与边界处理的正确性。
3. **利用受控故障注入验证异常路径。** 内存分配器的溢出处理和无内存可用（OOM）路径在常规运行中很难触发。通过在测试构建中引入轻量级的单次取页失败注入，并断言故障标志确实被消费（防止从已有缓存槽位分配而绕过取页路径），我们可靠地验证了分配失败时的状态回滚与无泄漏特性。
