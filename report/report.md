## 一、实验目的

本实验的主要目的是：

1. 理解 RISC-V 的中断与异常机制，掌握 `stvec`、`sepc`、`scause`、`sstatus`、`sscratch` 等 CSR 在 Trap 进入与返回中的作用，以及中断委托与 S 态处理框架。
2. 掌握 Trap 前后上下文的保存与恢复：理解 Trap frame 的布局，以及 `SAVE_ALL`、`RESTORE_ALL`、`__alltraps`、`__trapret` 如何与 C 语言处理函数衔接，形成“进入—保存—处理—恢复—返回”的闭环。
3. 实现断点异常、非法指令异常和 S 态时钟中断的处理，理解异常返回地址的调整与时钟中断的周期性重设。
4. 理解中断使能与屏蔽（`sstatus.SIE`、`sie`）及 `local_intr_save()` 在保护临界区中的作用，并将 Lab2 的物理内存管理迁移到带中断保护的新框架中。
5. 结合接口约束编写结构化提示词（PROMPT / RELY / GUARANTEE / SPECIFICATION），借助 AI 完成底层汇编与内核代码，并通过构建、运行和评测验证生成结果。

## 三、实验整体逻辑分析

### 2.1 本章节的逻辑主线

Lab1、Lab2 中内核只会“顺序执行”：启动、初始化内存、然后停在死循环里，它无法对外部事件做出反应，也无法在程序出错时接管控制权。Lab3 围绕**中断与异常（统称 Trap）**展开，要解决的问题是：当时钟到期、执行到断点或非法指令时，CPU 如何打断当前执行流、把控制权交给内核，内核处理完毕后又如何让被打断的程序“毫无察觉”地继续运行。

这条主线可以概括为一个闭环：

```text
事件发生 → 硬件写 sepc/scause/sstatus 并跳转到 stvec
        → __alltraps：SAVE_ALL 在内核栈上构造 Trap frame
        → trap(tf) → trap_dispatch：按 scause 最高位分为中断/异常
        → interrupt_handler / exception_handler：处理并按需修改 tf->epc
        → __trapret：RESTORE_ALL 恢复现场 → sret 返回 sepc
```

其中“现场如何保存与恢复”是机制，“遇到什么 Trap 做什么事”是策略。Lab3 只处理时钟中断、断点和非法指令三种最简单的情况，但这套入口与返回框架会在后续的系统调用、缺页异常和进程调度中被反复复用。

### 2.2 功能的逐步实现

1. 首先**迁移 Lab2 代码**（`page_init()` 与 Best-Fit）→ Lab3 依赖 Lab2，内核启动时 `pmm_init()` 先于中断初始化执行，物理内存管理不可用时内核无法正常启动；同时 Lab3 的 `alloc_pages()` 等接口加入了 `local_intr_save()`，迁移时需要保留这层保护。
2. 接着完成**功能模块一：Trap 入口与上下文恢复** → 这是所有 Trap 处理的公共通路。只有 `__alltraps` 能把 Trap frame 正确传给 `trap()`、`RESTORE_ALL` 能准确恢复现场，C 层的处理逻辑才有运行和返回的基础，否则任何一次 Trap 都会导致寄存器错乱或返回到错误位置。
3. 然后完成**功能模块二：中断与异常处理** → 在通路打通之后，按 `scause` 对 Trap 分类，实现断点与非法指令异常的输出和 `epc` 调整，以及时钟中断的重设、计数、统计输出与关机。
4. 最后在 `kern_init()` 中依次执行 `idt_init()`、`clock_init()`、`intr_enable()`，**开启时钟中断并整体验证** → 时钟中断是异步、持续发生的，必须等入口、恢复与处理函数都正确后才能打开，否则一次错误处理会在下一个时钟周期立即重复出现。

#### 实现迭代过程

本模块分两轮完成入口调用与现场恢复。提示词均采用四段式结构：在 `[PROMPT]` 中明确任务范围，在 `[RELY]` 中给出现场布局和调用接口，在 `[GUARANTEE]` 中列出需要完成的功能，并通过 `[SPECIFICATION]` 描述调用前后的状态及恢复要求。

##### 第一次迭代：Trap 入口调用

在 `SAVE_ALL` 后增加以下两条指令：

```asm
mv a0, sp
jal trap
```

此时 `sp` 指向已保存的 Trap frame。`mv a0, sp` 按调用约定传递第一个参数，`jal trap` 保存函数返回地址并进入 C 处理函数。函数正常返回后，栈指针保持调用前的值，执行流顺接 `__trapret`。处理函数通过 `tf` 访问和更新现场，恢复宏随后读取这些字段。

入口部分的 spec 重点约束参数地址与栈指针：传入的 `tf` 应等于调用前的 `sp`，使 C 代码能够直接访问汇编保存的现场；函数返回后 `sp` 应保持一致，使后续恢复宏仍能以同一地址读取 Trap frame。被打断程序原来的 `a0` 和 `ra` 已由 `SAVE_ALL` 保存，因此入口可以使用这两个寄存器完成参数传递与函数调用。

##### 第二次迭代：现场恢复

恢复位置由 `SAVE_ALL` 和 `struct trapframe` 共同确定。RV64 下每个槽位占 8 字节，32 个通用寄存器与 4 个 CSR 字段共占 288 字节。通用寄存器按编号对应槽位 0～31，槽位 2 保存的是分配 Trap frame 之前的旧 `sp`；槽位 32、33 分别保存 `sstatus` 和 `sepc`。因此，恢复时使用与保存时一致的编号和偏移，即可取回对应字段。

`RESTORE_ALL` 首先将槽位 32、33 的值读入 `s0`、`s1`，再写回 `sstatus`、`sepc`；随后从对应槽位恢复 `x1`、`x3` 至 `x31`，其中也包括借作中转的 `s0(x8)`、`s1(x9)`。最后从槽位 2 恢复旧 `sp`，完成通用寄存器的恢复。

恢复顺序取决于寄存器在恢复过程中的用途。CSR 需要通过通用寄存器中转，因此先完成 `s0`、`s1` 的中转操作，再恢复它们各自保存的值。其余读取均以当前 `sp` 为地址基准，若提前恢复旧 `sp`，相同偏移就会指向错误位置，所以将栈指针放在最后恢复；这条读取指令本身仍使用更新前的 `sp` 计算地址。

现场恢复部分的 spec 将 Trap frame 中的值定义为处理结束后应采用的最终现场。例如，模块二处理非法指令或断点异常时可以调整 `tf->epc`，恢复宏将调整后的值写回 `sepc`，使这一处理结果在返回时生效。恢复宏将 `sstatus` 中记录的状态写回，随后由 `sret` 根据 `SPP` 选择返回特权级、将 `SPIE` 的值恢复给 `SIE`，并跳转至 `sepc` 指定的位置。

### 功能模块二：中断与异常处理功能

**负责人：** 2412737-罗元伟

#### 模块功能描述

**需要实现/修改的函数：**

```c
void interrupt_handler(struct trapframe *tf);   // kern/trap/trap.c
void exception_handler(struct trapframe *tf);   // kern/trap/trap.c
static size_t trap_insn_len(uintptr_t epc);     // 新增辅助函数：计算 epc 处指令长度
```

**功能说明：**

`trap()` 收到 Trap frame 后由 `trap_dispatch()` 按 `tf->cause` 的最高位分派：最高位为 1（转为 `intptr_t` 后为负数）表示中断，交给 `interrupt_handler()`；否则为异常，交给 `exception_handler()`。两个函数处理完成后正常返回，由模块一的 `__trapret` 完成恢复与 `sret`。

按照指导书，本模块需要满足：

- **时钟中断（`IRQ_S_TIMER`）**：`clock_set_next_event()` 每次只设置一次触发时刻，必须在每次时钟中断中重新设置，否则只会收到一次中断；`ticks` 每次加一，达到 `TICK_NUM` 的整数倍时输出统计信息，累计输出达到 `SHUTDOWN_AFTER` 次后调用 `sbi_shutdown()` 关机。
- **其他中断**：区分类型并输出提示，无法识别的中断调用 `print_trapframe(tf)` 兜底。
- **非法指令（`CAUSE_ILLEGAL_INSTRUCTION`）与断点（`CAUSE_BREAKPOINT`）**：按规定格式输出，并按触发指令的实际长度推进 `tf->epc`，避免返回后重复执行同一条指令形成异常循环。RISC-V 指令长度由编码最低两位决定：最低两位为 `11` 时为 32 位指令，否则为 16 位压缩指令（如 `c.ebreak`），因此不能统一加 4。
- **其他异常**：调用 `print_trapframe(tf)` 兜底。

**实现要点：**（完整说明见 [模块二实现说明_lyw.md](模块二实现说明_lyw.md)）

1. **中断编号**：`interrupt_handler()` 用 `(tf->cause << 1) >> 1` 去掉最高位后按 `IRQ_*` 分类。
2. **时钟中断**：先调用 `clock_set_next_event()` 重设一次性定时器，再 `++ticks`；每到 `TICK_NUM`（100）的整数倍调用 `print_ticks()` 输出 `100 ticks`，输出次数达到 `SHUTDOWN_AFTER` 后调用 `sbi_shutdown()`。框架与指导书没有给出 `SHUTDOWN_AFTER`，在 `trap.c` 的模块二位置定义为 10（约 10 秒后关机）。
3. **其他中断**：软件中断、时钟中断、外部中断按 U/S/H/M 输出类型；未知编号输出 `Unknown interrupt: cause N` 并调用 `print_trapframe(tf)`。
4. **非法指令与断点**：输出 `Exception type: ...` 和 `... at 0x地址`，再由 `trap_insn_len()` 读取 `epc` 处的低 16 位，最低两位为 `0b11` 时推进 4 字节，否则推进 2 字节。评测内核中 `ebreak` 被汇编为 2 字节的 `c.ebreak`（编码 `9002`），非法指令 `.word 0x7b` 为 4 字节，统一加 4 会导致断点用例失败。
5. **其他异常**：调用 `print_trapframe(tf)` 兜底，不修改 `epc`。

## 六、实验总结与收获

### 对操作系统的理解

#### 1. 本实验中的重要知识点与 OS 原理的对应

**（1）Trap 机制 ↔ 中断、异常与中断向量**

- **原理**：中断是外部设备异步触发的事件，异常是当前指令同步引发的事件，系统调用是程序主动请求内核服务；三者都会让 CPU 暂停当前程序、进入内核，并通过中断向量找到对应的处理程序。
- **实验**：硬件在 Trap 时写入 `sepc`（返回地址）、`scause`（原因）、`sstatus`（之前的特权级与中断使能），并跳转到 `stvec`。`idt_init()` 让 `stvec` 以 Direct 模式指向唯一入口 `__alltraps`，再由 `trap_dispatch()` 根据 `scause` 最高位区分中断与异常。
- **关系与差异**：原理中常以 x86 的 IDT 为例，由硬件按向量号直接跳到不同处理程序；ucore 使用“单入口 + 软件分派”，RISC-V 虽支持 Vectored 模式，但对中断才按原因跳转，异常仍进入同一地址。实验也让“同步/异步”的区别具体化：异常处理需要考虑 `epc` 指向的那条指令本身，中断则在两条指令之间发生，返回时 `epc` 不需要调整。

**（2）Trap frame 的保存与恢复 ↔ 进程上下文与上下文切换**

- **原理**：课程中把上下文比作“存档/读档”：处理器状态保存在寄存器中，只要把寄存器存入内存、之后再写回，程序就能暂停后继续；由于无法预知程序用了哪些寄存器，最省事的做法是全部保存，且这段代码必须用汇编精确控制。
- **实验**：`SAVE_ALL` 在内核栈上分配 36 个槽位，保存 32 个通用寄存器与 `sstatus`、`sepc`、`sbadaddr`、`scause`；`RESTORE_ALL` 按相同偏移恢复，`sp` 最后恢复。这正是课程所说的“存档区”，`struct trapframe` 就是存档格式。
- **关系与差异**：Trap 的保存与恢复回到**同一个**执行流，进程切换（课程中的 `switch_to(from, to)`，后续实验的 `switch.S`）则恢复**另一个**执行流。Trap 发生的位置不可预知，必须保存全部寄存器；`switch_to` 是一次主动的函数调用，调用者保存寄存器已由编译器处理，只需保存被调用者保存的寄存器。两者都印证了课程中“切换并不免费”的结论：一次 Trap 就要做约 36 次存储和 33 次读取，这也是时钟中断频率不能设得过高的原因之一。

**（3）时钟中断 ↔ 分时复用与时间片轮转调度**

- **原理**：分时系统依靠时钟中断周期性地把控制权交回内核；在可抢占系统中，时钟中断是内核“强行”收回 CPU 的时机，时间片轮转（RR）在时间片用完时把进程排到队尾。课程给出的经验规则是让上下文切换开销保持在时间片的约 1%。
- **实验**：`clock_init()` 置位 `sie.STIE` 并通过 `sbi_set_timer()` 设置第一次触发时刻；`timebase = 100000`，在 QEMU 的 10 MHz 计时器下约为 10 ms 一次中断；`clock_set_next_event()` 是一次性设置，必须在每次中断中重设；`ticks` 记录中断次数。
- **关系与差异**：实验搭建了调度所需的“时钟心跳”，但只计数和打印，并没有在时钟中断中切换进程。S 态程序也不能直接写 `mtimecmp`，只能通过 SBI 请求 M 态固件设置定时器，这体现了特权级分层，是原理课中较少涉及的硬件细节。

**（4）中断使能与屏蔽 ↔ 临界区、原子性与特权级保护**

- **原理**：在单处理器上，关闭中断可以保证一段代码不被打断，是实现临界区互斥最直接的手段；但关中断属于特权操作，只能由内核执行，且关中断时间过长会影响系统的响应性。
- **实验**：`intr_enable()` / `intr_disable()` 控制 `sstatus.SIE` 这一全局开关，`sie` 控制各类中断的单独使能；`sync.h` 中的 `local_intr_save()` 先记录原来的中断状态再关闭中断，`local_intr_restore()` 只在原本开启时重新开启，从而支持嵌套使用。Lab3 的 `alloc_pages()`、`free_pages()`、`nr_free_pages()` 用它保护空闲链表，防止时钟中断处理过程与分配器交错修改同一数据结构。此外，硬件进入 Trap 时会自动清除 `SIE` 并把原值存入 `SPIE`，`sret` 再恢复，所以 ucore 的 Trap 处理默认不会嵌套。
- **关系与差异**：关中断只在单核上能保证互斥，多核环境下其他 CPU 仍可访问共享数据，还需要自旋锁等同步机制；实验中只有单核，因此关中断已经足够。

#### 2. OS 原理中重要但本实验未对应的知识点

**（1）系统调用与用户态/内核态切换**

课程中 OS 通过“系统调用 + 特权级”让程序无法绕过内核直接使用设备。Lab3 只有 S 态内核自身产生的 Trap：`riscv.h` 中虽定义了 `CAUSE_USER_ECALL`，但没有用户程序，也没有系统调用分发表；`SAVE_ALL` 只把 `sscratch` 用作暂存并清零，并没有根据它判断 Trap 来源、从用户栈切换到内核栈。完整的 U 态 → S 态陷入、参数传递与返回值写回 `tf->gpr.a0` 将在后续用户进程实验中出现。

**（2）缺页异常与请求调页、页面置换**

课程中的缺页处理流程是：MMU 发现页表项无效 → 触发缺页异常 → OS 换入页面并更新页表 → **重新执行**引起缺页的指令。Lab3 中 Load/Store/Fetch 类异常只由 `print_trapframe()` 兜底，没有对应处理。这里与本实验形成了有意思的对照：断点和非法指令处理后需要将 `epc` 推进到下一条指令，而缺页处理后 `epc` 保持不变以重新执行原指令；两者都依赖 Trap frame 的精确保存，区别在于对返回地址的处理策略。

**（3）进程调度与抢占式切换**

课程中调度的完整过程是“保存当前进程上下文 → 选择下一个就绪进程 → 恢复其上下文”，并涉及 PCB、进程状态、就绪队列以及 RR、MLFQ 等算法。Lab3 虽然有了时钟中断和上下文保存，但 `interrupt_handler()` 中的时钟处理只增加 `ticks`，没有 PCB、没有就绪队列，也没有在 Trap 返回前调用调度器切换到其他执行流，这部分要到进程管理实验才实现。

**（4）外设中断、中断控制器与中断嵌套**

原理中 I/O 设备通过中断通知 CPU 操作完成，涉及中断控制器、中断优先级、中断嵌套以及 DMA 等内容。Lab3 只使用了 S 态时钟中断，外部中断（`IRQ_S_EXT`）没有接入 PLIC，只做类型提示；Trap 处理期间 `SIE` 被硬件清零，不支持高优先级中断抢占低优先级中断的嵌套处理，也没有多核间的处理器间中断（IPI）。

【初稿，待各成员补充】

1. **把“不能改什么”写进提示词。** 模块一的提示词在 `[GUARANTEE]` 中明确不改变 `SAVE_ALL`、Trap frame 布局和 `trap()` 签名，并要求在未完成模块阻碍验证时如实说明。AI 因此没有为了“编译通过”而擅自补写模块二，也没有把单文件汇编成功描述为整体测试通过。
2. **`[RELY]` 要给出真实的数据布局。** `RESTORE_ALL` 的正确性完全取决于与 `SAVE_ALL` 的对应关系。提示词直接给出槽位编号（`sp` 在槽位 2、`sstatus`/`sepc` 在槽位 32、33），比让 AI 自行“理解”结构体更可靠，也便于人工逐行核对。
3. **约束恢复顺序比给出指令序列更有效。** 提示词没有直接给出汇编代码，而是说明“CSR 先经通用寄存器中转”“`sp` 作为读取基准必须最后恢复”等约束，再由 AI 推出具体指令顺序，这样既符合指导书要求，也能检验生成结果是否真的理解了约束。
4. **验证结果要区分环境问题和代码问题。** 模块一负责人在其环境中遇到汇编器不识别 `sbadaddr`，而在整合者本机上未复现；类似问题需要记录工具链版本，避免把环境差异误判为 AI 生成代码的错误。
