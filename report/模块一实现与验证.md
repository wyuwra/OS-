## 1. 实现位置与流程

实现位于 [pmm.c](../lab2_new/kern/mm/pmm.c) 的 `lab2 function1 2412832` 标记处；原 `YOUR CODE` 已替换为负责人的学号，`lab2 function1` 标记保留。函数签名保持为：

```c
static void page_init(void);
```

实现顺序：

1. 设置 `va_pa_offset`，再进行内核虚拟地址到物理地址转换。
2. 从设备树 getter 获取 RAM 起点和大小，检查零值、地址加法溢出。
3. 按 `PHYSICAL_MEMORY_END` 限制管理范围，再向下按页对齐。
4. 检查内核布局是否位于 RAM 内，按 `npage - nbase` 计算描述符数量。
5. 将描述符数组安排在 `end` 向上按页对齐后的位置，检查数组大小及容量。
6. 计算元数据之后的完整空闲页区间；没有完整页时明确 `panic`。
7. 初始化描述符的引用、标志、空闲块字段和链表节点，先将所有页标记为保留。
8. 调用当前分配器的 `init_memmap()`，仅开放确定可用的区间。
9. 输出报告 RAM 范围、管理结束边界、描述符位置及初始空闲页数。

空闲区之前的固件预留区、内核、启动栈、启动页表、描述符数组及含有已用数据的尾页保持保留。结构体大小使用 `sizeof(struct Page)`，没有写死。

负向测试的 PASS 表示正确拒绝无效布局，不表示故障内核正常启动。脚本以明确的预期信息判定，超时且没有目标信息时判为失败。

### 256 MiB 测试与官方测试的区别

官方 `test_page_init()` 要求 `npage == PPN(DTB 报告结束边界)`，没有考虑框架固定上界。256 MiB 时，本实现按约定只管理到 `PHYSICAL_MEMORY_END`。

因此该场景明确输出官方检查的 SKIP，改由新增的逐页检查核对实际边界、全部页面状态、计数及分配释放；128 MiB 和 64 MiB 场景仍调用原官方模块一测试。未修改官方测试函数内容。

## 8. 与操作系统原理的对应

| 原理知识 | 模块一中的对应 | 本实验的范围 |
|---|---|---|
| 物理页帧管理 | 以 4 KiB 为单位，建立 Page 描述符并登记空闲区。 | 单次启动初始化，实际选择空闲块由模块二分配器负责。 |
| 元数据与资源分离 | 描述符记录物理页状态，描述符数组自身也占用 RAM。 | 将自身占用页面保留，避免被分配覆盖。 |
| 地址转换 | PADDR、页号和描述符下标转换。 | 依赖现有内核直接映射偏移；不能推广为任意进程地址的转换公式。 |
| 边界与对齐 | 可用末尾向下对齐，元数据末尾向上对齐。 | 只开放完整页，保留含有已用数据的尾页。 |
| 安全初始化顺序 | 先保留全部页，再向分配器开放确认安全的区间。 | 输入和布局检查在写入描述符之前完成。 |

本模块尚未涉及的知识包括按需分页、页面换入换出、完整进程地址空间隔离、多段 RAM 管理、完整设备树保留区处理、并发分配保护及内存热插拔。启动页表已经由基础汇编设置，不能把本模块描述为从零实现完整虚拟内存系统。

## 9. 深入复查：保证初始化接口和验证结果可信

本轮逐项审查地址范围、容量检查顺序、保留状态、对齐和接口输入，未发现 `page_init()` 需要修改的功能逻辑。重点补强了测试中两个实际薄弱点。

### 9.1 分配器接管前的检查

First-Fit 的 `init_memmap()` 会重置输入页面的部分字段，所以只在分配器执行之后检查，不能证明交付前的全部状态正确。

验证器现在只在临时副本中，于 `pmm_manager->init_memmap()` 前调用检查函数，确认：

- 初始化空闲区只登记一次，数量大于零。
- 描述符指针属于数组，且按结构体元素边界对齐；区间长度不越界。
- 输入物理区间不覆盖内核和描述符数组，并正确到达管理结束边界。
- 全部描述符的标志精确为保留状态，引用计数和 property 为零，链表节点已自链接。

对无效输入的测试，还检查日志中不存在 `MODULE1 INIT_MEMMAP ENTERED`，证明失败路径没有提前把错误区间交给分配器。

成功判定会等到 `pmm_init()` 返回后的 `MODULE1 VERIFICATION COMPLETE`，同时要求接管检查、分配器自检和逐页布局检查均通过。256 MiB 场景对官方测试的适用范围仍按上文处理。

### 9.2 防止旧结果误导

每次验证在开始构建前把 `results.json` 更新为 `RUNNING`，记录唯一 run_id、源码 SHA-256 清单、当前案例和已完成结果。中途异常写为 `FAIL`；完整完成且原源码未被验证过程修改后才写为 `PASS`。

不能仅看到旧日志或部分 PASS 就认为本次运行全部通过，应先检查汇总文件的顶层 status 与相应源码版本。
