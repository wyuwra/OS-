## 1. 练习一的直接答案

入口文件为 [`../code/kern/init/entry.S`](../code/kern/init/entry.S)：

```asm
kern_entry:
    la sp, bootstacktop
    tail kern_init
```

`la sp, bootstacktop` 将启动栈顶部的地址放入栈指针寄存器 `sp`（`x2`），为后续 C 函数的栈访问提供基础。它取得的是符号的地址，而非读取该地址处的数据。本实验预留 8 KiB 启动栈；按照向低地址增长的栈使用约定，初始 `sp` 指向预留空间的高地址端。

`tail kern_init` 把控制权转移给内核初始化函数，不设置新的返回地址 `ra`（`x1`）。`kern_init` 完成初始化和输出后进入无限循环，不需要回到 `kern_entry`。两条指令按顺序建立启动栈，然后进入 C 代码。

寄存器定义及标准栈约定依据：[RISC-V psABI](https://riscv-non-isa.github.io/riscv-elf-psabi-doc/#_integer_register_convention)。伪指令语义依据：[RISC-V 汇编手册](https://github.com/riscv-non-isa/riscv-asm-manual/blob/main/src/asm-manual.adoc)。

## 2. 为什么 C 函数需要先建立栈

普通应用启动时，运行环境通常已经准备好栈等资源。本实验的内核入口需要自行建立它要使用的启动栈，不能把进入入口时的旧 `sp` 当成本内核拥有的栈。

实际单步中，在 `kern_entry` 处观察到：

```text
pc = 0x80200000
sp = 0x8001bd80
ra = 0x80000a02
```

这说明进入内核时 `sp` 并非零，但它尚未指向本内核预留的启动栈。执行入口栈初始化后：

```text
pc = 0x80200008
sp = 0x80203000
ra = 0x80000a02
```

随后 `kern_init` 的实际指令包含：

```asm
0x8020001a: addi sp,sp,-16
0x80200020: sd   ra,8(sp)
```

第一条分配 16 字节栈帧，第二条向栈中写入寄存器值。这就是必须先设置 `sp` 的实际证据。如果未建立正确的栈，后续写入可能破坏其他内存；在本例中，沿用旧栈不一定立即报错，但也不能据此认为它符合内核的内存布局要求。

并非所有 C 函数都一定使用栈，例如某些简单叶函数可能完全使用寄存器。本例是否使用栈，依据编译后的指令判断。

## 3. 启动栈的空间、方向与对齐

### 3.1 空间从哪里来

`entry.S` 把栈空间放在 `.data` 中：

```asm
.section .data
.align PGSHIFT
.global bootstack
bootstack:
    .space KSTACKSIZE
.global bootstacktop
bootstacktop:
```

[`memlayout.h`](../code/kern/mm/memlayout.h) 中 `KSTACKPAGE = 2`，[`mmu.h`](../code/kern/mm/mmu.h) 中 `PGSIZE = 4096`、`PGSHIFT = 12`，因此：

```text
KSTACKSIZE = 2 × 4096 = 8192 字节 = 8 KiB
```

`.space` 在汇编阶段预留空间；`la` 在执行阶段设置寄存器。两者是不同操作。

### 3.2 当前构建的实际布局

| 对象 | 地址或范围 | 依据 |
|---|---|---|
| 内核入口 | `0x80200000` | ELF 入口与符号表 |
| 启动栈 | `[0x80201000, 0x80203000)` | `bootstack`、`bootstacktop` |
| 初始内核栈指针 | `0x80203000` | GDB 单步 |
| `kern_init` 的栈帧底部 | `0x80202ff0` | `sp -= 16` |
| 保存的入口 `ra` | `0x80202ff8` | `sd ra,8(sp)` 与内存查看 |

```text
高地址
0x80203000 ─── bootstacktop；初始 sp，位于预留栈空间上边界
              │
0x80202ff8 ─── 保存的入口 ra：0x80000a02
              │  当前 kern_init 栈帧，共 16 字节
0x80202ff0 ─── 分配栈帧后的 sp
              │
              │  更深的函数调用继续向低地址使用栈空间
              ↓
0x80201000 ─── bootstack；预留栈空间下边界
低地址
```

栈顶标签位于预留空间之后是合法的：分配栈帧时先减小 `sp`，再在预留范围内访问内存。初始 `sp` 并不表示应直接向 `0x80203000` 写入数据。

### 3.3 对齐和边界

本目标中 `.align 12` 表示按 `2^12 = 4096` 字节对齐。8 KiB 栈大小也是 4096 的整数倍，因此栈顶部保持页对齐。标准 RISC-V ABI 要求进入函数时 `sp` 按 16 字节对齐，这里同样满足要求；`kern_init` 减去 16 后仍然满足。[RISC-V 栈约定](https://riscv-non-isa.github.io/riscv-elf-psabi-doc/#_integer_calling_convention)

页对齐并不表示已经启用分页，也不提供栈溢出保护。本代码只预留固定空间，未实现保护页或溢出检测。8 KiB 是本实验的配置值，不能推广为所有 RISC-V 内核的固定栈大小。

## 4. 从伪指令到最终机器指令

### 4.1 汇编目标文件中的形式

命令：

```bash
riscv64-unknown-elf-objdump -dr obj/kern/init/entry.o
```

关键输出：

```text
0:  00000117  auipc sp,0x0
    R_RISCV_PCREL_HI20 bootstacktop
4:  00010113  mv sp,sp
    R_RISCV_PCREL_LO12_I .L0
8:  00000317  auipc t1,0x0
    R_RISCV_CALL kern_init
c:  00030067  jr t1
```

`mv sp,sp` 是反汇编器给 `addi sp,sp,0` 使用的别名；`jr t1` 是 `jalr x0,0(t1)` 的别名。目标文件还没有最终链接，地址相关字段需要重定位，所以不能把这里的零立即数看成最终地址计算结果。

### 4.2 链接后的形式

命令：

```bash
riscv64-unknown-elf-objdump -d bin/kernel \
  --start-address=0x80200000 --stop-address=0x8020000a
```

实际输出：

```asm
80200000: 00003117  auipc sp,0x3
80200004: 00010113  mv    sp,sp
80200008: a009      j     8020000a <kern_init>
```

`auipc` 使用当前指令的 PC 加上左移 12 位的立即数：

```text
sp = 0x80200000 + (0x3 << 12) = 0x80203000
```

下一条的低位立即数恰好为零，因此显示为 `mv sp,sp`。它是当前地址布局的结果，并非所有 `la` 的第二条指令都会显示为无变化的移动。

目标文件里的 `tail` 占 8 字节，最终被链接器松弛优化成 2 字节的压缩跳转 `c.j`；反汇编器显示为 `j`。最终 `kern_init` 因而位于 `0x8020000a`。不能把一次 `stepi` 等同于执行一整条源码伪指令，本例的 `la` 需要两次机器指令单步。

链接松弛机制依据：[RISC-V psABI：Linker Relaxation](https://riscv-non-isa.github.io/riscv-elf-psabi-doc/#_linker_relaxation)。上述地址和指令长度由当前 GCC 8.3.0 构建验证；修改源码或工具链后应重新检查。

## 5. tail、call 和返回地址

`call` 的实际调用序列会设置 `ra`，让被调用函数能够返回到调用点之后；`tail` 的跳转不设置新的返回地址。在 `jalr x0,...` 中，返回地址写入目的寄存器是常零寄存器 `x0`，因此被丢弃；最终压缩跳转也不更新 `ra`。

本次单步结果：

| 时刻 | `pc` | `ra` |
|---|---|---|
| 执行 `tail` 前 | `0x80200008` | `0x80000a02` |
| 执行 `tail` 后 | `0x8020000a` | `0x80000a02` |
| `kern_init` 调用 `memset` 后 | `0x802004be` | `0x80200026` |

`tail` 不会把旧 `ra` 清零，也不保证此后的其他指令不修改 `ra`。`kern_init` 内部的 `jal` 正常建立新的函数返回地址。

`kern_init` 保存入口 `ra` 是本编译结果的函数序言行为。该函数最终没有返回路径，在本例的反汇编中也没有恢复这个栈槽后返回入口的指令；因此不能断言保存这个旧返回地址在当前程序语义上必不可少。这条存储最直接证明的是 C 代码确实使用了启动栈。

把 `tail` 改成 `call` 不一定会使当前程序立即失败，因为 `kern_init` 原本就不会返回；它会改变返回地址的语义，应通过反汇编和寄存器变化分析，不能把二者说成完全相同。

## 6. 链接、加载和开始执行

[`kernel.ld`](../code/tools/kernel.ld) 包含：

```ld
ENTRY(kern_entry)
BASE_ADDRESS = 0x80200000;
```

[`Makefile`](../code/Makefile) 使用 `objcopy -O binary` 生成 `bin/ucore.img`，并配置：

```text
-device loader,file=bin/ucore.img,addr=0x80200000
```

需要区分三个环节：

1. **链接布局：** 链接器安排节和符号地址，本构建的 `kern_entry` 位于 `0x80200000`。
2. **镜像加载：** QEMU loader 把原始二进制镜像放入指定内存地址。
3. **控制权转移：** 启动固件最终把执行流程转交内核，GDB 已验证到达入口。复位到入口的完整轨迹由成员二负责。

`ENTRY` 指定 ELF 的入口字段；它本身不会让 CPU 跳转，也不会完成镜像加载。[GNU ld：入口点](https://sourceware.org/binutils/docs/ld/Entry-Point.html)

`ucore.img` 是原始二进制，不能把 ELF 的入口字段当成 QEMU 从这个原始镜像中读取到的信息。链接布局、加载位置和启动固件交接需要相互匹配；若改变位置，必须检查重定位方式、代码所依赖的地址以及固件交接点，不能认为任意更改 loader 地址都能正常启动。

## 7. kern_init 与初始化语义

### 7.1 BSS 初始化

```c
extern char edata[], end[];
memset(edata, 0, end - edata);
```

`edata`、`end` 由链接脚本定义边界，在 C 中通过外部符号引用。根据本链接脚本，`edata` 位于 `.sdata` 之后，`end` 位于 `.bss` 之后；初始化代码将这一范围清零，支持未显式初始化的静态存储对象的零初值要求。

本构建中：

```text
edata = end = 0x80203008
清零长度 = end - edata = 0
```

ELF 节表也没有非空 `.bss`。实际调用前 `a0 = 0x80203008`、`a1 = 0`、`a2 = 0`。因此当前代码保留了 BSS 初始化流程，但本次没有清零任何非空区域。

启动栈属于 `.data`，位于 `edata` 之前，所以不在这次清零范围内。若把活动栈放进需要清零的范围，应重新安排清零与建栈顺序，否则可能覆盖当前调用所使用的栈内容；本实验布局避免了这种重叠。

### 7.2 优化调试中的参数显示差异

GDB 在 `memset` 入口打印过：

```text
n=18446744073709551615
```

不能仅凭这个显示断言发生了巨大长度的写入。构建使用 `-O2`，源码含 `while (n-- > 0)`；优化后的源码变量显示和真实机器级传参可能不一致，需要检查调用约定寄存器和实际控制流。

进一步验证的实际指令为：

```asm
0x802004be: beqz a2,0x802004ce
...
0x802004c6: sb   a1,-1(a5)
...
0x802004ce: ret
```

单步从 `0x802004be` 直接到达 `0x802004ce`，`a2` 始终为零，然后返回 `0x80200026`；存储指令未执行。因此机器级证据确定本次传入零长度并直接返回。这里无需改变编译优化来猜测程序是否写坏内存。

### 7.3 输出与不返回

`kern_init` 通过 `cprintf` 打印 `(THU.CST) os is loading ...`，随后执行 `while (1)`。QEMU 原始日志中已记录该输出。

`__attribute__((noreturn))` 告诉编译器该函数不会正常返回，属性本身不会生成无限循环。本例的不返回行为由循环实现；实际机器指令为 `0x8020003a` 跳回自身，连续两次单步后 `pc` 仍然保持这个值。[GCC 8.3 函数属性](https://gcc.gnu.org/onlinedocs/gcc-8.3.0/gcc/Common-Function-Attributes.html)

这是忙循环，不能等同于使用 `wfi` 等待中断。本练习也没有实现进程调度、完整异常处理、虚拟内存管理或用户态执行环境。

## 9. 与操作系统原理的联系

| 本实验观察 | 理论联系 | 当前范围 |
|---|---|---|
| 建立内核启动栈 | 执行上下文、函数调用和内存布局 | 单一启动栈，尚未涉及进程内核栈切换 |
| 链接与加载 | 地址布局与程序装载 | 固定布局和 QEMU loader，未实现通用可执行文件加载器 |
| BSS 初始化 | 静态存储对象初始化与运行环境准备 | 当前构建为空范围 |
| 固件交接后进入内核 | 引导与特权软件的职责衔接 | 完整复位轨迹由练习二验证 |
| 打印并进入循环 | 最小可运行内核 | 尚无调度、进程管理、分页管理或文件系统 |

这部分的学习价值是把源码意图、链接产物和寄存器变化对应起来。它为后续内核功能提供基础，但本实验本身还没有建立完整操作系统服务。
